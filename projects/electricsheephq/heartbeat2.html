overview

HeartBeat 2.0 is a Hermes plugin that schedules agent turns for reminders, recurring work, roles, and watcher checks. It uses code checks to determine whether work is due before starting a model turn, and provides commands such as `/pulse` to show upcoming work and trigger history.

  • Supports timed follow-ups, recurring checks, roles, and watchers.
  • Watchers can monitor files, processes, URLs, commands, or Hermes events.
  • Daily turn, message, and optional spending limits are configurable.

HeartBeat 2.0

Give your Hermes agent a working life between messages: wakes, watchers and roles, within daily turn and message caps.

No model runs until there's work: plain code checks every wake and watcher, and the agent gets a turn only when something is due or a watcher's condition is met. /pulse shows what's next; /pulse why <id> lists an item's recent triggers with their states and reasons.

Try it

  1. Allow it to start turns. Add this Hermes core key to your profile's config.yaml (it is kept outside the plugin's own settings on purpose), restart the messaging gateway, and send /pulse in your DM. It should say injection is allowed; if not, it shows the exact YAML to add.
    plugins:
  entries:
    heartbeat2:
      allow_gateway_injection: true
  2. Ask for something soon. In the same DM, write: "Remind me in 5 minutes to stretch." The agent arms a one-time reminder and replies with a one-line receipt saying when it will really fire.
  3. It writes first. Five minutes later the reminder arrives in that chat, from the agent, with no message from you in between. /pulse list and /pulse why <id> show what happened. During quiet hours (22:00–08:00 by default) a reminder waits until they end.

Next, hand it a role and watch its desk (Your first role), or have it watch something without a timer (What it feels like).

What it does

Put your agent in charge of something and it keeps working on it on its own time: in the same chat, on the same model, with everything it already knows, inside the budgets you set. It can watch a build, a log, a process or a URL and speak up only when something changed. When there's nothing worth saying, it keeps working quietly or rests.

  • Roles it owns. "You're in charge of the release notes." A role is a standing responsibility with a charter, a notebook the agent keeps between turns, and a rhythm the agent sets itself. It doesn't expire on a timer. You can hand one over, or the agent can take one on and tell you.
  • Its own time. Turn on own time and the agent gets regular turns with no assigned task. It looks at its desk (its roles, what's due, what it noticed, what budget is left) and decides: work on a role, follow something up, set up a watcher, tidy its notes or memory, or rest.
  • Follow-ups and watchers. A follow-up at a set time, a recurring check, a check-in after a long silence, or a deterministic watcher on a file, process, URL, read-only command or Hermes event. A watcher costs no model call until its condition is met. An agent watcher still looks right away while messages are held, then reports what matters once messages can be sent. Owner watchers wait as before.
  • Same conversation, same model. Every wake is a turn in the chat it belongs to, on that chat's own model. There is no side model, separate cron session or subagent.
  • Quiet work counts. A turn that researches, writes or prepares something without messaging you is real progress. Only wakes that keep finding nothing to do slow down, then pause and ask you once.
  • You set the budgets. Turns per day, an optional daily priced-spend limit, turns per role, messages per day, the unanswered mute and quiet hours are your settings. They hold back messages and spending, not initiative: while you're away or asleep the agent can keep working, and it tells you what matters when you're back. That work still uses turns: the agent's recurring work, roles and own time keep running (and billing) under the mute and quiet hours, unless you turn on sleep_after_days, which stops them in a chat you haven't written in for that long. Turn limits and the priced-spend check apply before each turn; the spend limit cannot stop a turn already running, and unpriced calls are not counted. Roles and own time don't expire on a timer. The agent can tighten its own limits but never widen yours.

See it work

One real run in a Telegram DM, captured as it happened (only reply-quote headers and two internal tool names are painted out). The owner switches a rounding function, starts the tests in a terminal, and asks the agent to speak up only if something fails.

1. Ask once. The agent arms a file watcher on the test log and says what it will do. Mid-run, /pulse status shows the watcher checking and no new messages.

2. It writes first. Two tests fail. About a minute later the agent posts the failures and the wrong values, with no message from the owner in between.

3. Same conversation. Asked "Is that my round() change?", it answers from the chat it already has, restores the Decimal version and reruns the suite: all 10 tests pass.

A second real run on the same profile shows roles and the desk (the reply-quote header is painted out).

4. Hand it a role. Asked to own the shop's release notes, a weekly batch of social drafts and a pop-up poster brief, the agent sets up three roles and sends a receipt. For each one it gives the rhythm, what it will and won't do without an OK, and a budget of one work turn a day. It also lists the facts it still needs, and anything missing stays TBC instead of being invented. (The release-notes row is above this crop.)

5. Its desk. /pulse desk shows the view the agent gets at the start of every role turn: each role's rhythm, last result and next turn, the day's messages and turns against your limits, and why messages are held right now. (A long desk lists the most recently updated roles and counts the rest.) Here it is quiet hours: the roles' turns still run, but their replies aren't sent. When you're back, the agent gets a short list of what it wanted to tell you and passes on what still matters.

What it feels like

A follow-up that reads the room.

You: Remind me at 4 to send the Acme invoice. Agent: Will do. I'll check in at 16:00.

16:00. Agent: It's 4. Did the Acme invoice go out? I can draft the email if that helps.

The wake runs inside your conversation. If you had written "sent it" at 15:10, the 16:00 turn would see that and stay silent. If the agent armed it with "cancel when I reply", any message from you cancels it outright.

A watcher that speaks only when something changed.

You: Keep an eye on the nightly build and tell me if it breaks. Agent: Watching the latest nightly run with a read-only gh run list check every 10 minutes. I'll only look when the result changes, and only message you if it failed.

02:10, after 14 unchanged checks that cost no model turns: Agent: The nightly build failed in tests/test_api.py (3 failures, all timeouts). Want me to dig in this morning?

During quiet hours the agent still looks right away, silently, within its turn and spend limits. One report-back turn per chat passes on what still matters once messages can be sent. Owner watchers wait until quiet hours end as before, unless you marked the watcher urgent and allowed urgent wakes through.

A pointless wake that catches itself. Say the agent set up an hourly "check the inbox" wake. After three empty checks it starts stretching the interval, and after six it pauses itself. The next time you talk:

Agent: I paused "check the inbox": six checks in a row found nothing. Keep, slow, stop, or turn it into a watcher? (/pulse keep|slow|stop|watch w_3f2a)

A check-in after a long silence (off by default). When it is on, the agent checks in once after a silence (24 h by default) and says how to turn check-ins off. It doesn't check in again until you've talked. This built-in check-in is not created in Desktop or TUI chats; you can still explicitly arm a silence wake there.

Why "2.0"

Heartbeats, as OpenClaw popularised them, made agents feel alive. They also produced a well-documented list of failures. We turned each one into a deterministic scenario in the benchmark suite:

Heartbeat-1.0 failure HeartBeat 2.0
Stops silently after compaction, sleep or restart The schedule and claims live in SQLite on wall-clock time. After a restart or sleep, missed fires collapse into one.
Duplicate or replayed deliveries Each fire is a durable compare-and-set claim. Only one wake can be in flight per chat, and a wake is never injected into a busy chat.
Message floods (one loop resent 189×) Daily caps on model turns and messages, spacing between wakes, a mute after unanswered messages, and an error ladder that ends in a pause.
"HEARTBEAT_OK" leaking into the chat The model never types a sentinel. It calls pulse respond notify=false, and the plugin makes the turn silent.
Messages to the wrong chat or person There is no destination parameter at all. A wake can only return to the chat that armed it, and only in DMs by default.
Most spend going to no-op ticks Watchers decide without a model call. The no-op governor backs off, then pauses.

Totals over 34 deterministic scenarios (B1 simulation driving the real engine; python -m bench.run --baseline --gate, source ca12767, v0.1.14 engine; the gate report records content digests). The comparison arm is a naive heartbeat-1.0 emulator built from documented failure reports. It is not a measurement of OpenClaw itself.

How it works

  you (/pulse) or the agent (pulse tool): what, when or what to watch, bounds
                                   │
                    durable schedule (SQLite in the profile)
                                   │
        time · silence · file · process · URL · command · Hermes event
                                   │
              nothing changed? ──► no model call, nothing sent
                                   │ due / changed / deadline
     gates: enabled · estop · paused · provider health · quiet hours ·
            sleep · unanswered mute · daily caps · busy · spacing · one in flight
                                   │
           one turn in the same chat, on the chat's own model
                                   │
                 pulse respond {outcome, notify, summary}
           notify=false ──► silent          notify=true ──► one short message
                                   │
          ledger + no-op governor (slow down → suggest a watcher → pause → ask once)

One poller per profile runs inside the messaging gateway that serves that profile and ticks every 5 seconds. Hermes loads every profile's plugins when a gateway starts; a gateway that does not serve a profile leaves that profile's schedule alone and delivers nothing for it. A file lock guarantees only one poller even when several Hermes processes share the profile. Chats served by an app backend of their own are scheduled by that backend under its own lock; the messaging gateway never touches them. Every fire is a durable claim with an attempt marker. In a messaging gateway, an accepted turn that never starts is tried three times, and a refused messaging injection backs off and is tried five times, before it is marked dead; app-backend wakes that the app accepted but never started wait instead and are never marked dead. Desktop and TUI wakes wait while the app session is closed, retrying every minute until it reattaches or the wake expires. A turn that started but never finished (a crash or restart) is recorded as interrupted. Hermes may auto-resume that wake turn, sometimes before heartbeat2's restart recovery has run; heartbeat2 keeps the replay silent either way, never counts it as a fire or delivery, and counts it as a model turn toward the daily cap.

Setup

Requires Hermes ≥ 0.21.6 and Python ≥ 3.11 on macOS or Linux. HeartBeat 2.0 delivers into messaging-gateway DMs (and group or topic chats when dm_only is off): Telegram, Discord, Slack, WhatsApp and the other gateway platforms. Desktop and TUI sessions also support wakes on capable Hermes 0.23+ hosts, using the same consent and limits. Chats that an app backend of their own serves (the Desktop app's standalone hermes serve, or the terminal TUI's backend) take one-time and recurring schedules; the backend schedules and delivers them while the app has the chat open, and a wake that comes due while it is closed fires once when the chat is open again, unless it expires first under its own expiry or catch-up rule. Watchers, keep-warm and own time there need a messaging chat. Known limits: one app backend per profile delivers, so if the terminal TUI and the Desktop app each run their own backend on one profile, the one started first delivers and wakes armed in the other's chats wait until it closes (the arm reply says so; #241); after an app backend restart, Hermes can drop a wake due right then (NousResearch/hermes-agent#159694); HeartBeat finds it missing from the queue and sends it once more, labelled late, and on a Hermes version whose queue it cannot read the wake waits until the app process exits (with a heads-up for owner-asked wakes). It is never lost.

Install with the command at the top, add the allow_gateway_injection key shown in Try it, and restart the messaging gateway. Then send /pulse in your DM. It shows:

  • whether the scheduler is running;
  • whether injection is allowed, with the exact YAML if it isn't;
  • your local time and quiet hours;
  • today's wakes, messages, cache counts and estimated cost (or token splits).

Your first role

A role shows its first results over a few hours, because it spreads its turns across the day. Start one once Try it works:

  1. Hand it a role. In your DM, for example: "You're in charge of my reading list. Summarise anything new between my messages, a few turns a day." The agent sets up the role and sends a receipt with its rhythm, what it will and won't do, and its daily budget. You can also set one up yourself with /pulse role self <charter> or /pulse role every 1d at 09:00 <charter>.
  2. Let it work. A role without a fixed time starts with its turns spread across the day by its budget: at the default 6 turns, about one every four hours. Quiet hours and the message limits hold its messages, not its work.
  3. Look at its desk. /pulse desk shows each role's last result and next turn, and today's messages, turns and cost against your limits. The agent sees the same desk.
  4. Adjust or stop it. /pulse budget <id> 2/day sets a role's daily turns; the agent can go under your number but never over it, and only this command raises it. A new budget changes how many turns the role takes a day, not how often they come: to spread them out, ask the agent to change its rhythm. /pulse pause <id> or /pulse cancel <id> stops one role, and /pulse off stops everything in the chat.

A role can name another role in the same chat with handoff_to: when it ends a turn with progress or done and a summary, the next role is brought forward within its usual limits and gets that result as work input. For example, research can hand off to drafting; an empty handoff_to clears the link.

Optional: set Own time (own_time_hours, for example 6) to give the agent regular turns with no assigned task. On Discord, WhatsApp or Matrix, set display.platforms.<platform>.tool_progress: off so silent turns don't post progress bubbles.

All other settings are in Settings ▸ Plugins in Hermes Desktop or in config.yaml. At start a rejected setting falls back to its default; on a live change it keeps its last good value, and your other changes still apply. /pulse status and pulse tool results name the ignored setting.

/pulse is a control panel, not conversation. Using it never counts as replying to the agent. Anything else you send counts as a reply, including a reaction or an edit on platforms that report them: it resets the unanswered mute and cancels wakes armed to stop when you reply. A reaction or edit counts only when its chat maps to one HeartBeat session; in a chat shared by several sessions (for example DM threads or topics) it is ignored. The other exceptions are listed under known issues: a message queued while the agent is busy on Signal or SimpleX, and a Codex app-server steer.

Your agent gets one tool, pulse (create · list · desk · update · pause · resume · cancel · respond · off), and the bundled heartbeat2-usage skill. desk lets it read its desk at any point in a turn, the same view as /pulse desk. The skill teaches it to:

  • rest one wake with action: pause, its id and pause_for: "12h" when it knows when to return; its timer never resumes a wake you paused or a chat you turned off, and it can resume a wake you paused with /pulse pause only during your own turn, never from its wake turns;
  • take on roles and keep working on them, follow up on what it started, and use its own time well;
  • treat your budgets as the rules it works inside, and message you only when it's worth your attention;
  • prefer a watcher to a timer whenever a deterministic check can tell "changed";
  • answer every wake with respond: outcome (no_change · progress · done · blocked · needs_attention), notify, a one-line summary, and optionally next_check and scratch notes for its next wake. done ends the wake. A silent turn (notify=false) that ends progress counts as real work; only no_change and blocked count toward slowing a wake down.

A wake turn is a normal turn in your chat: the agent has the same tools as in any other turn there. HeartBeat 2.0 does not restrict them, so arm wakes in conversations whose tools you are happy to have run while you are away.

Every arm returns a receipt with timing, any quiet-hour hold or unanswered mute, and expiry. A granted owner-requested agent reminder adds: "Counts as your own reminder: not muted or capped." A watcher you asked for adds: "You asked for this watcher: not muted; daily caps still apply." The agent relays that receipt instead of promising exact timing; a proposed wake is awaiting your OK.

Watchers available to the agent:

Watcher Fires when
file The file changes, or an appended line matches a pattern
process A process exits (PID reuse is detected)
url A GET response changes, or a pattern appears (10 s hard deadline, 256 KB cap)
command A read-only allowlisted command's output changes, it succeeds or fails, or it prints {"fire": true, …}
Hermes events A kanban task completes or blocks, a worker exits, a subagent finishes, the API errors, or someone reacts to or edits a message

Hermes events are selected by trigger.kind: kanban_completed, kanban_blocked, kanban_worker_exited, subagent_done, api_error, reaction (with an optional emojis filter) and message_edited. Kanban watchers can target one task with trigger.task_id, one board with trigger.board, or both. Reaction watchers can target one message with trigger.message_id.

Only probe and event watchers can carry a deadline: it is a one-time "nothing happened" fallback, and the watcher keeps going until it expires. Quiet hours can hold that fallback wake.

Guardrails, briefly

Every guardrail is configurable:

  • Recurring timers repeat at most every 15 minutes, or every 55 minutes when the agent arms one without a watcher. Watchers check at most once a minute.
  • Roles and own time don't expire on a timer; a role's explicit expiry can be up to 365 days out (max_reminder_days). Every other wake expires after 14 days at most, except a one-time reminder you ask for, which can be due up to 365 days out (max_reminder_days, never below max_lifetime_days). A reminder due later than 14 days stays deliverable for 14 days after its due time, so downtime at the due time follows the catch-up rule instead of expiring silently.
  • A wake that could not fire before it expires is refused, including an owner-silence wait or a probe's next check without a deadline. On create, an implicit lifetime stretches to fit, up to the maximum. Existing wakes keep their expiry; an edit past it is refused with a hint to set until.expires when extending can help, otherwise it names the maximum lifetime. Quiet hours count at the real dispatch time for one-shot times and watcher deadlines. A timed quiet override chains into the default quiet hours if they still apply when it ends. A one-shot outside the catch-up window is refused; one due now fires on the next check. A timed resume that cannot fit ends the wake with a notice. Receipts name the silence duration and are at most 240 characters; long ones end with an ellipsis.
  • The daily model-turn cap holds watchers until capacity frees, including on a new local day. Under the daily message cap your watchers wait the same way, and agent watchers run silently with their messages held. Your unedited one-shot reminders, including one-time reminders you ask for in chat, bypass both caps.
  • After 2 unanswered messages, agent one-time follow-ups and built-in check-ins drop their occurrence. The agent's recurring work, roles, own time and watchers keep running with their messages held; quiet hours and the daily message cap hold their messages the same way. Wakes you armed, and one-time reminders you ask for in chat (the agent marks them owner_asked), still fire unless the agent edited their trigger, timing or note. A watcher you ask for in chat, such as "tell me if my flight is delayed", is marked the same way and still sends its alerts; the daily message cap and quiet hours hold them as usual; a watcher-only conversion you requested with /pulse watch keeps owner status. Held matches merge, keeping the latest payload; pauses preserve them and expiry is visible in /pulse why.
  • A wake turn that carries untrusted data, such as a log line or a web page, cannot arm new recurring work. Neither can a later wake turn that is shown a held report such a turn wrote.
  • Hermes' emergency stop halts every wake.
  • /pulse off stops everything in that chat, and only you can turn it back on.

Cost

A wake turn is an ordinary model turn in that conversation. It is billed like a message, and its size is your conversation's context size: on a long-running agent that can be 100–200k input tokens per wake. Watchers, gates and skipped wakes cost nothing. /pulse status and /pulse ledger show warm/cold wake counts and estimated cost when priced, otherwise the in/cached/written/out split. The ledger also counts no_verdict turns. Start with watchers and long intervals.

Prompt cache

Claude marker routes use Hermes' 5m/1h/auto setting; GPT-5.6+ and GPT-6.x on OpenAI API routes use 30m. The Codex OAuth route is reported as unknown until learned. Other routes learn a conservative TTL only after both warm and cold gaps are observed. On Claude models, whose caches last at least 5 minutes, a cache miss less than 5 minutes after the previous call means the prompt changed, not that the cache expired, so it doesn't count as a cold gap. Agent recurring intervals near the TTL snap below it with downward jitter, respecting floors. Owner wakes, cron and anchored repeats retain their timing. Cache lines show the effect and warm interval.

Keep a long chat warm: /pulse warm on. On a long conversation, the first message after the cache expires rewrites the whole prompt at the cache-write price (about 2x input on a 1h Claude cache), where a warm message pays the read price (about 0.1x). /pulse warm on turns on keep-warm for that one chat: just before the cache would expire, HeartBeat sends a tiny silent turn ("reply [SILENT]", no tools) that reads the cache and keeps it alive, so the next real message stays warm. If you don't come back before it pauses, those pings were spent for nothing, so the pause is set with that in mind.

  • It pings only where a ping can pay off: on routes whose cache lasts 30 minutes or more, while the chat's prompt is at least keep_warm_min_tokens, and while you've written in the last keep_warm_idle_hours. When you come back, it starts again.
  • Any real turn in the chat (yours or a wake's) moves the next ping out, so an active chat gets no pings. It never pings a cache that has already gone cold.
  • Pings are silent, aren't wake turns, and don't count toward wake turns, messages, active items or the daily priced-spend limit for the agent's own turns. /pulse status and /pulse ledger show them on their own row with their cost.
  • Only you turn it on or off (/pulse warm off); the agent can't. When the route doesn't report the cache lifetime, HeartBeat uses the longest gap it has seen stay warm on that route. Claude caches last 5 minutes or 1 hour, so once a Claude route has stayed warm past 15 minutes HeartBeat counts on the hour, even on a route new after a model switch (a shorter warm gap can be timing skew on a 5-minute cache), and a shorter cold miss (a compaction or a rebuilt system prompt changes the prompt) doesn't stop keep-warm. Two pings in a row whose first model call finds the cache cold do, until a reply on that route reuses the cache after more than 15 minutes or you run /pulse warm on again. On other models' routes, a cold miss shorter than the longest warm gap stops it. /pulse warm, /pulse status, /pulse list and the agent's list say why no ping is due. When keep-warm has been unable to ping for two hours because the cache lifetime is unknown or short, caching is off, or two pings in a row found it cold, the agent tells you once, on the next message you send (not while HeartBeat is off in the chat). A model switch starts the two hours again for the new model. A small context or your rest is not a reason in itself, since keep-warm wouldn't ping then anyway, but time you spend resting still counts toward the two hours.
  • Hermes has no per-turn output cap for plugins, so the ping asks for a one-word reply rather than enforcing it.
  • Hermes builds that include its own prompt-cache warmer (NousResearch/hermes-agent#156455, merged after Hermes 0.23.2) keep most chats' caches warm by themselves, and HeartBeat can't yet see that schedule. In a chat that warmer handles, turn /pulse warm off, so the chat doesn't run two warmers that each bill their pings. Keep it on where Hermes doesn't warm: it skips requests it can't replay, such as Claude with a fixed thinking budget (budget_tokens) and mixture-of-agents routes. HeartBeat will step aside on its own once Hermes lets plugins read the warm schedule (#23).

Security and privacy

Disclosure — wakes and watchers run full turns on the conversation's own model, billed like any message; command watchers run allowlisted read-only commands without an approval prompt; URL watchers make the GET requests you configured; state stays in the profile's plugin-data; no telemetry. Command environments use Hermes' sanitizer on an allowlisted base and carry no provider, bot or GitHub tokens unless you name one for an allowed command in probe_command_env; gh uses its own hosts.yml or keyring. URL watchers always block cloud metadata, and block private/local addresses unless url_allow_private is enabled, checking every hop at connect time. File watchers honor Hermes read blocks at arm/update and every check, including rotation. Helpers run in the watcher's profile scope.

Command watchers:

  • use an allowlisted environment that does not pass proxy or custom-CA variables yet, unless you grant them in probe_command_env;
  • run only argv prefixes from your allowlist. The default is gh pr view/checks, gh run view/list, git ls-remote/status/log;
  • run with no shell and no terminal;
  • refuse output, config, editor, browser and mutating flags and verbs, including gh --jq/-q and --template/-t;
  • have the whole process group killed after 30 seconds.

The argv guard is not a sandbox: only allow programs you trust to be read-only. URL watchers refuse credentials in the URL and send no cookies, auth headers or proxy settings. Wake turns keep the conversation's normal tools and permissions. Full threat model and limits: SECURITY.md.

The default command allowlist still permits gh -R HOST/... and git ls-remote <url> to reach any host the machine can reach; the current release keeps this exception.

Closed-window notices

The owner can set plugins.entries.heartbeat2.settings.notify_via to birdie:assistant (then restart Hermes). Install and configure the notifier plugin separately. Blank disables notices; invalid values are ignored. /pulse status shows whether the notifier is connected.

After a chat's oldest closed-window hold reaches ten minutes, HeartBeat sends one short count-and-time notice per held episode. It includes no wake titles or contents. The chat's quiet-hours override (or profile quiet hours when there is no override) and daily message cap defer it; the unanswered mute does not. Off or paused chats send no notice. A queued notice counts as one message, without increasing the unanswered count. One wait gets one notice. Before a notice is sent, the wait ends when a wake in that chat runs (an accepted injection) or no wake is held there any more. After a notice is sent, it lasts until a wake runs in the reopened chat or the owner writes there, and at most a day after the notice, so a window closed for days gets at most one notice a day.

queued means accepted by the notifier's bus, not read by anyone. Failed sends retry after five minutes for the first three attempts, then hourly, stopping after 24 hours. A timeout or Birdie's “can't reach birdie” error shows may repeat: the notifier couldn't confirm the send, and the message may already have gone, so a retry can duplicate it. notifier not ready means no sending-profile token is available yet; Birdie obtains one after that profile's first turn.
